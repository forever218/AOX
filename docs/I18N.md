# Internationalisation (i18n) · one language, one distribution

- **Status**: shipped. The copy phase is complete — every user-facing string in `src/` and
  `gui/src/` is English and wrapped in `t(...)` / `tf!(...)`, and `locales/zh.toml` carries the
  Chinese catalogue (686 entries).
- **Code**: `src/i18n.rs` (runtime core), `build.rs::emit_lang` (the registry generator),
  `locales/<code>.toml` (the catalogues).
- **One line**: **the language is chosen at compile time** (`AOX_LANG`), **English is the source
  language**, and a non-English distribution embeds exactly one catalogue.

---

## 1. The model in one picture

```
                       build time                                         run time
 ┌───────────────────────────────────────────────────┐       ┌────────────────────────────────┐
 │ AOX_LANG=zh                                       │       │ src/i18n.rs                    │
 │   → build.rs::emit_lang                           │       │   t("Ready")                   │
 │       • CODE    = "zh"                            │   ───► │   → zh?   table lookup         │
 │       • CATALOG = include_str!("locales/zh.toml") │       │   → en?   return input         │
 │   → writes $OUT_DIR/langs.rs                      │       │   → miss? source shown through │
 └───────────────────────────────────────────────────┘       └────────────────────────────────┘
```

The root crate's `build.rs` is the **only** place that emits a language registry. The GUI does
not have its own; it calls `aox::i18n::t` / `aox::tf!` through the lib. So `AOX_LANG` set once on
the `cargo` command line decides the language for `aox.exe` **and** `aox-gui.exe` together.

---

## 2. Three design decisions

Derived from the module docs at the top of `src/i18n.rs`; they are the *why* behind everything
below.

1. **English is the source language.** Every user-facing string in the code **is** the English
   wording. Those literals play two roles at once: the final text of the `en` build, and the
   **key** every other language's catalogue looks up. Consequence: adding a language changes
   **zero** lines of source code — you add a variant and a catalogue, never a literal.

2. **The English build has zero drift.** Under the source language `t()` returns its argument
   unchanged and `tf!` is byte-for-byte `format!`. So `AOX_LANG=en` produces output identical to
   "before i18n existed", and not one existing test needs editing.

3. **There is no in-app switch.** The language is fixed when the binary is built
   (`build.rs` `include_str!`s exactly one catalogue). Installing the English build gives you
   English throughout — UI, error messages, system prompt and tool descriptions all switch
   together; installing the Chinese build gives you Chinese throughout, and the **other**
   languages' strings never even enter the binary.

## 3. The registry `build.rs` generates

`build.rs::emit_lang` writes this tiny file into `$OUT_DIR/langs.rs`, which `src/i18n.rs`
`include!`s:

```rust
// Generated by build.rs, do not edit by hand.
pub const CODE:    &str = "zh";                     // AOX_LANG, lower-cased
pub const CATALOG: &str = include_str!("…/locales/zh.toml");  // "" for the source language
```

Rule of thumb:

| `AOX_LANG` | `CODE` | `CATALOG` | Result |
|---|---|---|---|
| `en` (default) | `"en"` | `""` (nothing embedded) | literals are the wording; `t()` is the identity |
| `zh` | `"zh"` | `include_str!("locales/zh.toml")` | lookups against that one table |
| anything else | the code | — | **the build fails** if `locales/<code>.toml` is missing |

Rebuild triggers are declared, so switching the variable is enough — no `cargo clean` needed:

```rust
cargo:rerun-if-env-changed=AOX_LANG
cargo:rerun-if-changed=locales
cargo:rerun-if-changed=locales/zh.toml      // the file actually used
```

A **missing catalogue fails the build**, on purpose: "a language was named but no catalogue was
shipped" is exactly the trap that compiles fine and only shows up as an all-English screen at
runtime.

## 4. Writing a translatable string

```rust
use crate::i18n::{t, tf};                      // CLI (src/)
// gui/ uses the same items through the lib:
//   aox::i18n::t("…")   /   aox::tf!("…", …)

// plain text — no placeholders
println!("{}", t("Ready"));

// with arguments — positional `{}` only
println!("{}", tf!("Collapsed {} tool calls", n));
```

### 4.1 The positional-`{}` rule (the one thing to actually remember)

`t()` returns a runtime string, so `format!` cannot be used on it (`format!` needs a
compile-time literal). `tf!` therefore walks the template and fills **bare `{}`** in order via
`i18n::fill`. It has **no syntax** for width or named forms:

```rust
tf!("score: {}", format!("{:.1}", x))     // ✅ pre-format to a string, pass as an arg
tf!("score: {:.1}", x)                    // ❌ {:.1} is not recognised — it stays literal
tf!("{name} joined", name = n)            // ❌ named placeholders unsupported
```

The catalogue value and the source must agree on the **number** of `{}`. Too few arguments
leaves the placeholder visible rather than eating half the sentence (a visible `{}` is the clue
that the catalogue dropped an argument); extra arguments are ignored.

### 4.2 What is *not* translated (by design)

`t()` takes `&'static str` — **compile-time literals only**. Anything built at runtime is passed
through untouched:

- dynamic data: plugin names, file paths, model output, tool arguments;
- protocol/self-produced tokens compared or matched by code (e.g. `HOST_PREFIX`, `ATTACH_MARK`);
- test fixtures that pin UTF-8 / JSON round-trips.

Two files therefore still contain Chinese **on purpose**: `src/selftest.rs` (UTF-8 fixture
strings) and `src/i18n.rs` (the `中文` self-designation, see §6). They are the only remaining CJK
in the source, and the leak gate in §9 is expected to report exactly them.

## 5. The catalogue format — `locales/<code>.toml`

A flat TOML table, **English key → translation**:

```toml
# locales/zh.toml  (English source -> Chinese)
"Ready" = "就绪"
"Collapsed {} tool calls" = "已折叠 {} 次工具调用"
```

Key rules — the catalogue must match the compiler's view of the literal, not its source text:

| Concern | Rule |
|---|---|
| Outer quotes | **not** part of the key (`"Ready"` in code → key `Ready`) |
| Escapes | the key is the **decoded** runtime string: a real newline, not the two characters `\n` |
| Line continuations | a `\`-continued multi-line literal collapses to one key with real newlines |
| Placeholders | positional `{}`, **same count** as the source; order may differ |
| Missing entry | the source string shows through (visible clue; see §7) |

The current Chinese catalogue is `locales/zh.toml` (686 entries). For the source language there
is **no** `locales/en.toml` — embedding one would mean stuffing another language's strings into
the English build, which `build.rs` and a unit test both forbid (§8).

## 6. `Lang` — the enum behind a code

`src/i18n.rs`:

```rust
pub enum Lang { #[default] En, Zh }         // En is the source language
pub const SOURCE: Lang = Lang::En;

impl Lang {
    pub fn code(self)        -> &'static str { … "en" / "zh" }       // on-disk / CLI code
    pub fn native_name(self) -> &'static str { … "English" / "中文" } // self-designation, never translated
    pub fn from_code(s: &str) -> Option<Lang> { … }                  // en, zh, cn; collapses zh-CN / en_US
}
```

- `native_name` is always written **in that language itself** and is never translated: someone who
  reads only Chinese must still recognise 中文 inside an English diagnostic.
- `from_code` takes only the primary subtag, so `zh-CN` and `en_US` collapse to `zh` / `en`.
- `lang()` reads `langs::CODE` and **panics loudly** if the code is unrecognised — the build
  script already proved the catalogue exists, so the only remaining failure is "`build.rs` and
  `Lang::from_code` have drifted apart", and that must be said out loud rather than silently
  falling back to English.

---

## 7. Lookup semantics (`t` / `fill`)

- Source language (English) → the input is returned **unchanged** (zero drift).
- Any other language → table lookup; **a miss falls back to the English source**. Better to reveal
  one English string than to show a blank or mojibake — and the string that shows through is
  precisely the clue for "which entry was missed". `tools/check_i18n.py` roots these out.
- A **malformed** catalogue does not crash the program: `map()` prints
  `[i18n] failed to parse locales/<code>.toml: …` and falls back to the source language.

## 8. Tests always run in the source language

```rust
fn is_source() -> bool { cfg!(test) || lang() == SOURCE }
```

Several hundred existing tests assert English output ("the result should contain some particular
word"). Because i18n is the identity transform for the source language, **not one of them needs
editing** under `cargo test` — `cfg!(test)` pins them to English regardless of `AOX_LANG`. Release
builds are unaffected (`cfg!(test)` is only true in a test build).

The unit tests in `src/i18n.rs` pin the invariants, including the important one:

```rust
#[test] fn catalog_presence_matches_source() {
    if lang() == SOURCE {
        assert!(langs::CATALOG.is_empty());   // the source build must embed no catalogue
    } else {
        assert!(!langs::CATALOG.is_empty());  // a non-source build must embed one
    }
}
```

This single test binds `build.rs`, `SOURCE` and the enum together: an English build carrying a
catalogue, or a Chinese build carrying none, both fail.

## 9. Verifying a build

While the source still contains a few deliberate CJK strings, the gate is a **leak scan**:

```bash
python tools/check_i18n.py          # summary + "leaks" list; exit 1 if any leak/missing
```

`tools/check_i18n.py` walks `src/**/*.rs` and `gui/src/**/*.rs`, skips comments and
`#[cfg(test)]` blocks, and reports every CJK literal **not** wrapped in `t(...)` / `tf!(...)`.
After the copy phase the expected output is the deliberately-CJK pair from §4.2 (`selftest.rs`
fixtures + `i18n.rs`'s `中文`) and nothing else. A literal can be exempted in place with a
trailing `// i18n-ignore` comment when it is **data**, not copy.

> ⚠️ Note: this tool's docstring and its optional `locales/en.toml` cross-check date from the
> earlier *Chinese-source* design and are now legacy. Treat its **leak list** as the signal.

A quick end-to-end smoke test per language:

```bash
AOX_LANG=en cargo run -- /demo      # sample output renders in English
AOX_LANG=zh cargo run -- /demo      # the same command renders in Chinese
```

Anything that stays English under `AOX_LANG=zh` is either a genuine miss (look for a `{}`-count
mismatch or a stray-quoted catalogue key) or a value that is deliberately dynamic (§4.2).

## 10. How to add a language — three steps

Say you are adding French (`fr`).

**① Add the catalogue** `locales/fr.toml`, English key → French value:

```toml
"Ready" = "Prêt"
"Collapsed {} tool calls" = "{} appels d'outils repliés"
```

Keys must match the English literals **character for character** (decoded, no outer quotes);
placeholder counts must match. To seed it, the same tooling that produced `zh.toml` works:
`tools/str_l10n.py dump <file>` lists the English literals, and `toml <acc.json> <out.toml>`
emits a catalogue from an accumulated `English → translation` table — just keep a *separate*
accumulator file per language.

**② Teach `src/i18n.rs` the code** — add a variant and one arm in each of three places:

```rust
pub enum Lang { #[default] En, Zh, Fr }
// Lang::code:        Lang::Fr => "fr",
// Lang::native_name: Lang::Fr => "Français",     // written in French, never translated
// Lang::from_code:   "fr" => Some(Lang::Fr),
```

Also extend the two tests that enumerate languages (`lang_codes_roundtrip`,
`every_lang_has_native_name` iterate `[Lang::En, Lang::Zh]`) so the new variant is covered.

**③ Build it:**

```bash
AOX_LANG=fr cargo build -p aox        # CLI
AOX_LANG=fr cargo build -p aox-gui    # GUI
```

That is the whole recipe. If you forget step ①, step ③ fails at build time with a message that
repeats it:

```
AOX_LANG=`fr` has no matching catalogue: …/locales/fr.toml
Adding a language takes three steps: ① locales/fr.toml; ② add a Lang variant
and a from_code arm in src/i18n.rs; ③ build with AOX_LANG=fr.
```

## 11. How to build a language version

`AOX_LANG` defaults to `en`, so **omitting it builds English**. Put it before `cargo` to pick a
language; it applies to every build script in the invocation, and `rerun-if-env-changed` means
switching the value recompiles what it must — no `cargo clean` required.

```bash
# ── English (default) ───────────────────────────────────────────────
cargo build                      # CLI only (workspace default-members = ["."])
cargo build -p aox-gui --release # GUI

# ── Chinese ─────────────────────────────────────────────────────────
AOX_LANG=zh cargo build -p aox                          # CLI, debug
AOX_LANG=zh cargo build -p aox-gui --release            # GUI, release

# ── both binaries, release, one language ────────────────────────────
AOX_LANG=zh cargo build --release --workspace           # → target/release/{aox,aox-gui}.exe

# ── run without producing a named release ───────────────────────────
AOX_LANG=zh cargo run -- /demo                          # CLI
AOX_LANG=zh cargo run -p aox-gui -- --demo              # GUI
```

Notes.

- `cargo build` alone builds **only the CLI** — the workspace's `default-members` is `["."]`.
  Use `-p aox-gui` or `--workspace` for the GUI.
- Language is decided by the **`aox` lib's** build script, and the GUI links that lib, so a single
  `AOX_LANG` covers both `.exe`s.
- The release **installer** (`tools/build_installer.sh`) runs `cargo build --release --workspace`
  internally and does not set `AOX_LANG`, so it currently produces **English** packages. To ship a
  Chinese installer, export the variable for the whole script:

  ```bash
  AOX_LANG=zh bash tools/build_installer.sh
  ```

  (Parameterising `build_installer.sh` / the `.iss` scripts with a language, so an en package and
  a zh package can be produced side by side, is a possible follow-up.)

## 12. Traps

- **The key is the decoded literal body, without the outer quotes.** Passing the quoted token
  (e.g. `"Ready"` with its quotes) to the decoder silently produces a key that can never match —
  the English build (identity) hides it, and only the Chinese build shows the fallback.
- **`tf!` is positional-only.** `{:.1}` / `{name}` / `{:>9}` must be pre-formatted into a string
  argument (§4.1).
- **Real newlines, not `\n`.** A catalogue key holding the two characters `\n` will not match a
  literal that decodes to an actual newline.
- **Multi-line and `\`-continued literals are easy to miss** when grepping by hand. Trust the
  leak gate (§9) over a plain text search.
- **Re-emit the catalogue after editing the translation table.** `locales/zh.toml` is generated
  from an accumulated table (`.workbuddy/l10n/acc.json` via `tools/str_l10n.py toml`); editing the
  accumulator without re-emitting leaves the built catalogue stale.
- **Don't translate what code compares.** Strings used in equality checks, CLI parsing or
  persisted formats (`.jsonl`) are data — wrap only presentation, or you will change behaviour.
